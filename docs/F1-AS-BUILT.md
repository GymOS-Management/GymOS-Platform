# F1 — as built

What differs from [`F1-DESIGN.md`](F1-DESIGN.md), and what building it taught. The design document
stands as written; this records the decisions taken with a keyboard rather than on paper.

## Everything in the design landed

All ten design decisions (D1–D10) are implemented as specified. Scope matches §2 exactly: nine routes,
twenty API operations, no screen built on data that does not exist yet.

Verified: `pnpm typecheck`, `pnpm lint`, `pnpm format:check`, **22 unit tests**, **20 E2E tests** (ten
journeys × desktop and mobile), `pnpm build`, dependency policy — all green against a real backend at
`v0.5.1` on real PostgreSQL 17.

## Decisions taken while building

### The two-rendering `DataTable` duplicates row text in the DOM

Lists render a desktop table _and_ mobile cards, hiding one with CSS. That is the right call — a
JS-breakpoint switch would break SSR and add layout shift — but it has a real cost: every row's text
exists twice, so a naive `getByText` matches an element nobody can see. Three E2E failures came from
this before it was understood.

The cost is paid in the tests, where `visibleText()` filters to what the operator can actually see, and
documented at both ends (`data-table.tsx`, `tests/e2e/README.md`). Worth knowing before adding any
DOM-based tooling — a screenshot differ or a scraper will see the same doubling.

### Sharing one session across E2E tests would be actively wrong here

The idiomatic Playwright optimisation — sign in once, reuse via `storageState` — is unsafe against this
backend. The refresh cookie **rotates on every use** and a replayed one is treated as an attack that
revokes the chain, so a shared cookie file is stale the moment the first context refreshes. The failure
would present as random logouts and look like a bug in the console.

Each test signs in fresh instead, and the _test_ backend runs with a raised sign-in limit
(`Security__RateLimiting__SignInAttemptsPerWindow=500`) because twenty fresh sign-ins exceed the
production-appropriate ten per minute. Nothing about production configuration changes. Discovering this
was the rate limiter proving it works.

### `totalCount` arrives as `number | string`

The backend's OpenAPI generator declares `int32` as `number | string`, so the generated types say so.
Coerced once in `Pagination` rather than by hand-editing `api.d.ts` — editing generated types is exactly
the drift AD-12 forbids. Worth raising with the backend later; it is a generator quirk, not a contract
decision.

### Closing the mobile drawer belongs at the click, not in an effect

The first version closed the drawer in a `useEffect` watching the pathname. React's linter objected, and
correctly: the drawer closes because the operator tapped a link, so the link says so. Fewer renders and
one less thing to reason about.

### Tailwind 4, and no `tailwind.config.ts`

§4.2's file tree lists `tailwind.config.ts`, which is Tailwind 3's shape. Tailwind 4 configures theme
tokens in CSS (`src/app/globals.css`), so that file does not exist. The tokens themselves are
shadcn-shaped semantic variables, redefined per theme — dark mode is a token swap, not a second set of
components.

### TypeScript pinned to 5.x, ESLint to 9.x

The current majors (TypeScript 7, ESLint 10) are ahead of what `openapi-typescript` and
`eslint-plugin-import` declare support for, and shipping unmet peers to save a version bump is a poor
trade. Recorded in `docs/DEPENDENCY_POLICY.md` with the reason.

## Notes for whoever picks this up

- `AGENTS.md` and `CLAUDE.md` in the repo root are **generated by `next dev`**, not written by hand.
  They warn that this Next.js major differs from older conventions; leave them in place.
- The `.github/workflows/ci.yml` E2E job checks out **both** repositories, because the suite is only
  meaningful against a real API. Its contract-drift step regenerates the types and fails on a diff —
  the frontend half of the backend's own R13 snapshot gate.
- One thing to watch: `src/lib/api/client.ts` holds the access token in a module variable. That is
  deliberate (D3) and is why `bootstrapSession()` exists, but it means any future server component that
  needs API data cannot reuse this client — it would have no token. Server-side data fetching needs the
  BFF conversation first, not a workaround.
