# F2 — Billing Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the frontend share of M3 — plan catalogue, gym subscription lifecycle, and invoices — after making the backend contract declare the three headers it enforces.

**Architecture:** Task 1 is backend (GymOS-Backend): marker metadata on the endpoints that read `Idempotency-Key`, `If-Match` and `X-Confirm-Action`, plus an OpenAPI operation transformer that turns each marker into a declared parameter. Tasks 2–10 are frontend (GymOS-Platform): regenerate types from that contract, extend the hand-written client with an idempotency key, then build six screens on F1's existing components. Every screen is a client component using React Query, exactly as F1 does.

**Tech Stack:** .NET 10 / Microsoft.AspNetCore.OpenApi (Task 1). Next.js 16 App Router, React 19, TypeScript, TanStack Query v5, Tailwind 4, shadcn-style components, vitest, Playwright (Tasks 2–10).

## Global Constraints

- **Design of record:** `docs/F2-DESIGN.md`. Decisions are referenced as D1–D8 below; do not re-decide them.
- **This Next.js major differs from older conventions.** `AGENTS.md` requires reading the relevant guide in `node_modules/next/dist/docs/01-app/` before writing App Router code. Route params are `Promise<T>` unwrapped with `use(params)` — see `src/app/(admin)/gyms/[gymId]/page.tsx`.

- **Money is never formatted with a hard-coded 2 decimals** (D2). `Money` supports 0- and 3-minor-unit currencies.
- **Overdue is never computed on the client** (D3). Use the server's `isOverdue`.
- **Commit after every task.** Conventional-commit prefixes, as both repos use.
- **Backend checks:** `dotnet build GymOS.Backend.slnx` (0 warnings) and the named test project.
- **Frontend checks:** `pnpm typecheck && pnpm lint && pnpm format:check && pnpm test`.

```csharp
using Microsoft.OpenApi;

namespace GymOS.WebApi.Extensions;

/// <summary>
/// Declares, on the endpoint itself, the headers that endpoint's pipeline enforces — so the OpenAPI
/// document says what the API actually requires.
///
/// <para><b>Why markers rather than inference.</b> The three requirements are enforced in three
/// different places: <c>Idempotency-Key</c> by middleware keyed on <c>IIdempotentCommand</c>,
/// <c>If-Match</c> by a <c>PreconditionHeaders.IfMatch</c> read inside the handler, and
/// <c>X-Confirm-Action</c> by a comparison inside the command. None of them is visible as endpoint
/// metadata, so nothing can derive the answer at document-generation time. Declaring it at the
/// mapping — one call beside the route it describes — is the honest version, and the R13 snapshot
/// gate turns any omission into a reviewed diff rather than a silent one.</para>
/// </summary>
public static class RequiredHeaders
{
    /// <summary>Marker metadata; the name carried here is the header the operation will declare.</summary>
    internal sealed record RequiredHeader(string Name, string Description);

    public const string IdempotencyKey = "Idempotency-Key";
    public const string IfMatch = "If-Match";
    public const string ConfirmAction = "X-Confirm-Action";

    /// <summary>AD-39: the operation replays a stored outcome rather than repeating its effect.</summary>
    public static TBuilder RequiresIdempotencyKey<TBuilder>(this TBuilder builder)
        where TBuilder : IEndpointConventionBuilder =>
        builder.WithMetadata(new RequiredHeader(
            IdempotencyKey,
            "A caller-chosen key, one per intent (a UUID is recommended). Retrying with the same key "
            + "replays the stored outcome instead of repeating the effect. Omitting it is "
            + "400 `idempotency.key_required`."));

    /// <summary>Optimistic concurrency: the `rowVersion` read from the resource, as a strong ETag.</summary>
    public static TBuilder RequiresIfMatch<TBuilder>(this TBuilder builder)
        where TBuilder : IEndpointConventionBuilder =>
        builder.WithMetadata(new RequiredHeader(
            IfMatch,
            "The strong ETag from the resource you read. Omitting it is 428; a stale value is 409."));

    /// <summary>AD-6 step-up: a value the caller can only know by having read the resource.</summary>
    public static TBuilder RequiresConfirmAction<TBuilder>(this TBuilder builder)
        where TBuilder : IEndpointConventionBuilder =>
        builder.WithMetadata(new RequiredHeader(
            ConfirmAction,
            "Step-up confirmation, echoing the resource's own identifier (a gym's slug, an invoice's "
            + "number). A header rather than a body field so it survives DELETE and cannot be replayed "
            + "by a script that never read the resource."));

    /// <summary>Turns whatever markers the endpoint carries into declared header parameters.</summary>
    internal static void Declare(OpenApiOperation operation, IEnumerable<object> endpointMetadata)
    {
        foreach (RequiredHeader header in endpointMetadata.OfType<RequiredHeader>())
        {
            operation.Parameters ??= [];

            operation.Parameters.Add(new OpenApiParameter
            {
                Name = header.Name,
                In = ParameterLocation.Header,
                Required = true,
                Description = header.Description,
                Schema = new OpenApiSchema { Type = JsonSchemaType.String },
            });
        }
    }
}
```

```ts
/**
 * Money, in the reader's locale and the amount's own currency.
 *
 * `Intl.NumberFormat` derives the number of decimals from the currency code, which is the point:
 * JPY has none and KWD has three, and the backend's `Money` rounds to exactly those minor units
 * (AD-42). Hard-coding two would misprint both.
 *
 * The amount is accepted as a string as well as a number because the API's JSON numbers are read as
 * either depending on the schema — the same reason F1's `totalCount` is `number | string`.
 */
export function formatMoney(
  amount: number | string | null | undefined,
  currency: string | null | undefined,
): string {
  if (amount === null || amount === undefined || !currency) {
    return '—';
  }

  const value = typeof amount === 'string' ? Number(amount) : amount;

  if (!Number.isFinite(value)) {
    return '—';
  }

  try {
    return new Intl.NumberFormat(undefined, { style: 'currency', currency }).format(value);
  } catch {
    // An unrecognised code must not blank the screen; show the number and the code as given.
    return `${value} ${currency}`;
  }
}
```

```ts
/**
 * One idempotency key per operator intent (F2-DESIGN.md D1).
 *
 * Call this where the operator confirms — in the dialog's submit handler — and hold the result for
 * that mutation. Calling it inside a `mutationFn` would mint a new key on every React Query retry,
 * which is the failure this exists to prevent.
 *
 * A UUID, per the backend's API_STANDARDS §10: keys are scoped `(tenant, operation, key)`, so two
 * callers choosing the same non-random key for the same operation collide.
 */
export function newIdempotencyKey(): string {
  return crypto.randomUUID();
}
```

```tsx
interface MarkPaidIntent {
  paymentReference: string | null;
  /**
   * D1: the key belongs to the intent, so it is created by the caller below and carried into the
   * mutation. Calling `newIdempotencyKey()` inside `mutationFn` would mint a fresh key on every
   * React Query retry, presenting the backend with a second payment rather than a retry of the
   * first — the exact failure AD-39 exists to prevent.
   */
  idempotencyKey: string;
}

const markPaid = useMutation({
  mutationFn: ({ paymentReference, idempotencyKey }: MarkPaidIntent) =>
    invoices.markPaid(invoice.id, paymentReference, invoice.rowVersion, idempotencyKey),
  onSuccess: (updated) => {
    queryClient.setQueryData(['invoices', 'detail', updated.id], updated);
    void queryClient.invalidateQueries({ queryKey: ['invoices'] });
    // Paying the last open invoice of the current period settles a PastDue subscription, so the
    // subscription card is stale the moment this succeeds.
    void queryClient.invalidateQueries({ queryKey: ['subscriptions'] });
    toast.success('Invoice marked paid');
  },
});

// The dialog's submit handler — one key per press of the button.
async function handleMarkPaid(paymentReference: string | null): Promise<void> {
  await markPaid.mutateAsync({ paymentReference, idempotencyKey: newIdempotencyKey() });
}
```
